# meco-etl

ETL scripts for data assets serving the internal site (`internal.electiondata.my`) and the public API (`api.electiondata.my`).

All scripts read from upstream parquets in `PATH_RESULTS_HEADLINE` (set in `.env`) and write into local staging folders that mirror the R2 bucket structure. Upload functions push the staged files to R2 and purge the Cloudflare cache.

---

## Run order

The five core pipeline scripts have a strict dependency chain driven by the parquets they read and write.

```
api_candidates.py
      │
      ├── api_parties.py
      │         │
      │         └── api_elections.py
      │                    │
      │                    └── api_seats_current.py
      │
      └── api_results.py
```

| Step | Script | Reads | Writes |
|------|--------|-------|--------|
| 1 | `api_candidates.py` | `consol_ballots.parquet`, `consol_stats.parquet` | `candidates.parquet` |
| 2 | `api_parties.py` | `candidates.parquet`, `lookup_party.parquet`, `lookup_coalition.parquet`, `lookup_dates.parquet` | `parties.parquet`, `coalitions.parquet` |
| 3 | `api_elections.py` | `candidates.parquet`, `parties.parquet`, `consol_ballots.parquet` | `elections_by_seat.parquet`, `elections_stats.parquet` |
| 4 | `api_results.py` | `candidates.parquet` | `results/{seat}/{date}.json` |
| 5 | `api_seats_current.py` | `elections_by_seat.parquet`, `lineage/*.parquet` | `seats/current/*.json` |

`api_results.py` only needs `candidates.parquet` so it can technically run after step 1, but the conventional order is to run it after step 3.

`api_seats_current.py` also requires the lineage parquets (`lineage/filter.parquet`, `lineage/desc.parquet`, `lineage/parlimen_geo.parquet`, `lineage/dun_geo.parquet`), which are pre-generated by `api_seats_lineage.py` and don't need to be regenerated on every run.

## New election checklist

Pending elections need no flag. Once upstream `consol_ballots.parquet` has the candidates with `result = 'pending'`, the pipeline treats the election as post-nomination, pre-results. The steps below are the manual ones.

### Nomination day

1. **Elections dropdown.** Add the election by hand to `internal.electiondata.my/elections/dropdown.json` (gitignored, not generated), at the top of its state's block, e.g. `{"state":"Melaka","type":"dun","election":"SE-16","date":"2026-11-14"}`. `api_elections.py` uploads it to both buckets.
2. **Homepage.** Make the state map images `og-image/{state}-se{n}.png` and `-dark.png` (1200×630) with the snippet in `paper-meco-maps/playground.ipynb` (one cell per election; filter to the state and adjust the zoom). Save them to `internal.electiondata.my/og-image/`, add the election at the top of `internal.electiondata.my/latest.json`, then run `api_latest.py`.
3. **Run the pipeline** in the order above.
4. **Lake and catalogue.** Run `lake_results_headline.py`. The new pending rows land in the national and state headline files, so set `data_as_of` to the nomination date in `internal.electiondata.my/catalogue/index.json` for `headline-{ballots,stats}` and `headline-{ballots,stats}-state-{code}`, then run `api_catalogue_results_headline.py`.

### When the voter roll is available

5. **Voter roll.** Add the state to `dun_rolls` in `api_seats_current.py`, keyed by the full-name slug suffix (e.g. `"-melaka"`, not `"-mlk"`), pointing at `{PATH_VR}{code}_se{n}_{year}.parquet`. Re-run `api_seats_current.py`.

### Polling day

6. **Election-night constants.** Point `api_election_night.py` at the new election: `DATE`, `ELECTION`, `STATE`, `STATE_CODE`, plus the state name and seat count in the docstrings. On run it also sets `data_as_of` in `catalogue/index.json` for `headline-{ballots,stats}` and the state's `headline-{ballots,stats}-state-{code}` slices, which is what the catalogue shows as `last_updated`.

The `last_updated` field in `template-catalogue/headline-*.json` is overwritten by `api_catalogue_results_headline.py` and has no effect.

## Script reference

### Pipeline scripts

#### `api_candidates.py`
Merges consolidated ballot and stats parquets into a single `candidates.parquet` that is the shared input for most downstream scripts. Also generates `candidates/dropdown.json` and `candidates/all.json` for internal use, and per-candidate JSONs for the public API.

#### `api_parties.py`
Aggregates candidate-level results up to party and coalition level. Applies lineage normalisation for both parties and coalitions: the numeric prefix of a uid (e.g. `001` from `001-UMNO`) is the stable key, so parties or coalitions that have renamed over time are grouped together under their current uid, with the historical name preserved in `known_as_uid` / `known_as_coalition_uid`. Outputs `parties.parquet` (one row per party × election × state) and `coalitions.parquet` (same, collapsed to coalition level).

Generates two JSON outputs:
- `parties/dropdown.json` — flat list of all parties and coalitions that have ever contested, for use in dropdowns
- `parties/all.json` — full time-series of results keyed by `party-{uid}` or `coalition-{uid}` (e.g. `party-001-UMNO`, `coalition-001-BN`)

#### `api_elections.py`
Builds per-election JSON files (by-party summary, by-seat results, aggregate stats) for internal and public API use. Also generates the by-elections JSON. Reads `parties.parquet` for the by-party summary and `candidates.parquet` (via DuckDB) for the by-seat results.

#### `api_results.py`
Splits `candidates.parquet` into per-seat, per-date JSON files (`results/{seat}/{date}.json`) for the internal site's results view.

#### `api_seats_current.py`
Generates the current seat holder view. Joins `elections_by_seat.parquet` (winners only, from `api_elections.py`) with the lineage tables to show each seat's current holder alongside historical boundary context. Produces `seats/current/all.json` and per-seat JSONs for the public API.

---

### Lineage and map scripts

#### `api_seats_lineage.py`
Pre-generates the lineage parquets consumed by `api_seats_current.py`. Tracks how seat boundaries have changed across delimitation years, producing three artefacts per seat type:
- `geo` — maps each current seat to its dominant geospatial ancestor
- `filter` — maps each current seat to the past seat names from which its results should be drawn
- `desc` — human-readable English/Malay descriptions of boundary changes

Run this whenever delimitation data changes. Does not need to be re-run on every results update.

#### `api_catalogue_maps.py`
Generates catalogue JSON entries for map delimitation and subdivision datasets, combining templates with live file sizes, row counts, and sample data.

#### `api_og.py`
Renders Open Graph images (one per parliamentary constituency and state) using Plotly and uploads them to R2. Skips seats whose images already exist.

#### `api_redelineation.py`
Uploads pre-generated redelineation JSON files to R2. No data transformation — purely a sync operation.

#### `api_latest.py`
Uploads the homepage's `latest.json` (maintained by hand, gitignored) and the OG images it references. Images already live are skipped; new ones are uploaded from `og-image/`. If an image is neither live nor local, the script stops before uploading `latest.json`, so the homepage never points at a missing image. To replace an image that is already live, upload it with `api_og.upload_og_images()`.

---

### Data lake scripts

#### `lake_results_headline.py`
Writes headline election results to the data lake in CSV, Parquet, and Excel formats, sliced by scope (all, federal only, by-elections, per-state). Independent of the main pipeline — reads directly from upstream parquets.

#### `api_catalogue_results_headline.py`
Generates catalogue JSON entries for the headline results datasets published to the lake. Reads the catalogue index and per-file stats/samples from `lake.electiondata.my/`.

---

### Utilities

#### `helper.py`
Shared utilities: `write_parquet`, R2 client setup, bulk upload/copy, Cloudflare cache purge, slug generation, and column schema constants.
